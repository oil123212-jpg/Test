# Phase 1 착수 전 검토 및 실행 계획

> 2026-10-31 웹 전환: [최신 설계 및 검토 기준](../../docs/web_transition.md). 아래는 기존 Python/디바이스 기반 기록입니다. 제공자·개인정보 검토는 유지하고, Pi 장치 및 기기 인증 항목은 웹 기준으로 대체합니다.

작성일: 2026-10-13. 현재 Phase 0의 코드와 검증 기록을 바탕으로 정리했습니다. 이 문서의 검토 항목은 아직 충족된 것으로 간주하지 않습니다. 제공자 최신 문서를 조회하려 했으나 이 클라우드 환경에서는 접속되지 않았습니다. 아래 공식 문서와 실제 프로젝트 설정/계약을 직접 확인해 결정 기록을 남겨야 합니다.

## 1. 시작할 수 있는 작업과 외부 전송 허용 시점

Phase 1 인터페이스 구현, 모의 WebSocket 서버, 인증/동의 상태 테스트는 지금 진행할 수 있습니다. 실제 제공자 연결은 성인 개발자 또는 합성 음원으로 제한한 개발 환경에서 계정·API 이용 요건을 확인한 뒤 진행합니다. 실제 아동 음성의 외부 전송은 아래 제공자·개인정보·동의·인증·철회 요건이 모두 확인될 때까지 차단합니다.

현재 `PrivacyPolicy.validate_data_processing_permission(external=True)`는 동의 상태와 관계없이 오류를 발생시킵니다. 구현 편의를 위해 이 차단을 삭제하거나 환경변수 하나로 해제하지 않습니다. 성인/합성 음원용 시험 경로와 아동 서비스 경로의 정책을 구분하고, 시험용 경로가 제품에서 사용되지 않도록 배포/권한을 분리합니다. 입력 음성이 아동인지 자동으로 판별할 수 있다고 가정하지 않습니다. 시험 참여자와 음원을 통제하는 운영 절차가 필요합니다.

| 단계 | 허용할 작업 | 아직 허용하지 않을 작업 |
|---|---|---|
| A: 기반 개발 | mock 연결, 합성 PCM 생성, 인증/동의/취소 테스트 | 실제 아동 데이터 전송 |
| B: 제공자 개발 연동 | 이용 요건 확인 후 성인/합성 음원으로 제한된 API 시험 | 아동에게 기기를 제공하는 시험 |
| C: 아동 시험 준비 | 제공자/법무/보호자 동의/보안/기기 검증 완료 후 별도 계획 승인 | 확인되지 않은 설정/동의로 자동 전송 |

## 2. 우선순위와 산출물

| 우선순위 | 항목 | 담당 역할 | 남길 결과 | 통과 기준 |
|---|---|---|---|---|
| P0 | 제공자 아동 이용/보관 요건 | 서비스 책임자 + 제공자 담당자 | 제공자별 검토표, 계약/문의 답변, 확인 날짜 | 만 3~6세 대상 사용과 해당 API 데이터 처리 조건을 구체적으로 확인 |
| P0 | 국내 개인정보 처리 설계 | 서비스 책임자 + 법률/개인정보 전문가 | 데이터 흐름표, 법적 근거, 동의/국외 이전/보관 문서 | 미확인 사항이 있는 아동 전송을 금지하고 필요한 조치를 정의 |
| P0 | 보호자 확인·동의·철회 | 백엔드 + 보호자 화면 담당 | 동의 상태 계약, 확인 방식, 철회 시험 기록 | 미동의/철회/조회 실패에서 전송 0건; 승인 가짜 구현 없음 |
| P0 | 기기 인증·중계 서버 | 백엔드/보안 담당 | 인증 프로토콜, 키 관리, 만료/철회/접근 제어 시험 | 기기 ID만으로 권한 발급 불가; 장기 제공자 키가 기기에 없음 |
| P1 | 실제 Windows/Pi 오디오 | 디바이스 담당 | 장치별 실행 기록과 수동 청취 결과 | 녹음/재생/주파수 fallback/중단 후 재사용 확인 |
| P1 | Realtime 계약·오디오 형식 | AI 연동 담당 | 모델/이벤트/포맷/토큰 시험표 | 선택한 전송 방식의 지원과 오류/취소 동작을 실제 확인 |
| P1 | 로그·삭제·장애·비용 | 백엔드/디바이스 담당 | 유출 검사, 장애 결과, 사용량/상한 문서 | 개인정보 로그 없음; 버퍼/비용 제한; 자동 무제한 재연결 없음 |
| P2 | 아동 시험 운영 | 서비스 책임자 | 감독·중단·장치 음압·사고 대응 계획 | 아동에게 노출하기 전에 검토 완료; 제공자 정책에 맞는 응답 보호 조치 |

P0는 실제 아동 데이터를 보내기 위한 선행 요건입니다. 이 요건 확인을 기다리는 동안 A단계 개발은 계속할 수 있습니다. P2의 VAD/에코 제거 전체 구현이나 책 읽기/감정 분석/장기 기억을 Phase 1 완료 조건으로 확장하지 않습니다. 다만 실제 아동 시험을 한다면 별도의 응답 안전성/감독 계획이 필요합니다.

## 3. 제공자 조건: 보호자 동의와 별도로 검토

### 구체적인 확인 방법

1. OpenAI와 향후 Gemini 각각의 **API 이용 약관·아동/청소년 개발 지침·데이터 처리 조건**을 확인합니다. 소비자용 앱 이용 연령과 개발자가 만드는 API 제품의 조건을 혼동하지 않습니다.
2. 서비스 설명을 작성합니다: 대상 만 3~6세, 보호자 관리 디바이스, 원본 음성 전송 후보, 기본 저장 없음, 장기 기억 없음, 개발/상용화 구분.
3. 문서에 답이 없으면 제공자에 이 설명으로 문의하고 답변을 보관합니다. 문의 메일 전송은 이 작업에서 수행하지 않았습니다.
4. 조직/프로젝트 단위 설정에서 실제 지원 모델, 엔드포인트, 보관 제어와 승인 상태를 확인합니다. 문서에 기능이 있다고 해서 현재 계정에 활성화됐다고 가정하지 않습니다.
5. 다음 표를 채웁니다. 확인 날짜, 문서 버전/URL, 적용 계약, 프로젝트의 실제 설정을 같이 기록합니다.

| 질문 | 확인할 근거 |
|---|---|
| 만 3~6세용 음성 디바이스에 API를 사용할 수 있는가? | 해당 API/제품에 적용되는 정책, 필요 시 제공자 답변 |
| 만 13세 미만 대상에 별도 제한이나 승인 요건이 있는가? | 아동/청소년 개발 지침, 계약 |
| Zero Data Retention 등 별도 보관 제어가 필요한가? 현재 프로젝트에 승인됐는가? | 제공자 조건과 조직/프로젝트 설정 |
| 선택한 Realtime 엔드포인트가 그 보관 제어를 지원하는가? | 엔드포인트별 데이터 처리표 |
| 음성/전사문/오용 모니터링 데이터가 어디에 얼마나 보관되는가? | 제공자 데이터 문서와 계약 |
| 학습 사용, 접근 주체, 재위탁, 국외 이전과 삭제는 어떻게 처리되는가? | DPA/계약/제공자 답변 |
| 필요한 아동 응답 보호·모니터링 조치를 어떻게 충족할 것인가? | 개발 지침과 운영 설계 |

확인 출발점:

- [OpenAI 개발자 문서](https://developers.openai.com/)에서 Realtime, Under 18, Your data 지침 확인
- [OpenAI 이용 정책](https://openai.com/policies/usage-policies/)
- [OpenAI 비즈니스 약관](https://openai.com/policies/business-terms/)
- [Gemini API 문서](https://ai.google.dev/gemini-api/docs) 및 [추가 약관](https://ai.google.dev/gemini-api/terms)

이 문서는 위 조건의 현재 내용이나 충족 여부를 확인했다는 의미가 아닙니다. 조건이 불명확하거나 사용이 허용되지 않으면 아동 데이터 경로를 열지 않습니다.

## 4. 국내 개인정보·동의·삭제

### 방법

1. 실제 데이터 흐름을 한 장으로 정리합니다: 마이크 → Pi 메모리 → 자체 중계 서버 → AI 제공자 → 음성 출력. 서버 중계안에서는 자체 서버도 음성을 처리한다는 점을 포함합니다.
2. 각 구간별 수집 항목/목적/저장 위치/접근자/보관기간/전송 국가/수탁·제3자 관계를 기록합니다. 음성, 전사 이벤트, 기기 ID, 접속 로그, 보호자 동의 증빙을 모두 포함합니다.
3. 법률/개인정보 전문가에게 이 표로 검토를 요청합니다. 주요 질문은 만 14세 미만 법정대리인 동의·확인 방식, 국외 이전 근거/안내, 처리방침, 권리 행사, 보관·파기, 안전성 확보조치입니다. 음성의 생체인식 활용 여부 등 처리 목적에 따른 분류도 확인합니다.
4. 보관기간은 데이터마다 정합니다. 음성/전사문 기본값은 저장 안 함, 세션 메모리는 세션 종료 때 제거합니다. 운영 로그는 크기 제한 외에 기간 제한도 정하고 구현합니다. 법정 보관 필요성이 있는 동의 증빙은 대화 데이터와 별도 관리합니다.
5. 삭제 요청이 로컬 파일뿐 아니라 서버/DB/백업/제공자 측 데이터에 어디까지 반영되는지 정의합니다. 법적 보관 예외와 즉시 삭제할 데이터를 구분하고 결과를 보호자에게 안내합니다.

확인 출발점: [국가법령정보센터](https://www.law.go.kr/)의 최신 개인정보 보호법·시행령, [개인정보보호위원회](https://www.pipc.go.kr/)의 관련 가이드. 이는 법적 적합성 판정이 아니라 실제 검토할 항목입니다.

### 동의 흐름의 구현 계약

- 보호자 채널에서 법정대리인 확인과 동의 내용을 안내합니다. 단순 로그인, 체크박스, QR 스캔만으로 법정대리인 확인이 완료됐다고 간주하지 않습니다.
- 동의 기록에는 목적/항목/정책 버전/확인 방법/동의 시각/철회 시각/최소 연결 식별자를 둡니다. 원본 음성과 불필요한 신분증 사본은 동의 증빙으로 수집하지 않습니다.
- 서버가 확인한 결과만 GRANTED로 반영합니다. 기기는 자체적으로 승인 상태를 생성하지 않습니다.
- 서버 조회 실패, 오래된 동의 정보, 정책 버전 불일치, 미요청/대기/철회는 모두 외부 전송 거부입니다. 검증한 동의 정보를 언제 다시 확인할지 기한과 갱신 규칙을 정합니다.
- 철회 시 서버의 활성 세션 권한을 제거하고 기기는 새 프레임 전송 중단 → 전송 큐 제거 → 응답 취소 → 연결 종료 → 버퍼 정리를 수행합니다. 이미 외부로 전송된 데이터는 취소로 회수되지 않으므로 보관/삭제 조건을 별도로 확인합니다.

### 시험과 통과 기준

모의 서버로 미요청/대기/철회/동의 서버 장애/정책 변경을 주입합니다. 각 상태에서 허용되지 않은 음성 프레임이 **0건** 전달되는지 서버 측에서도 확인합니다. 진행 중 철회 시험에서는 거부 정책이 적용된 후 새 프레임이 전송되지 않아야 합니다. 원격 철회의 전달 지연은 측정해 기록하고, 즉시 철회를 보장한다고 과장하지 않습니다.

현재 로컬 삭제 함수는 앱 전용 디렉터리의 허용된 파일만 삭제합니다. Phase 1 서비스용으로는 사용자/기기별 접근 제어와 전용 저장 경로를 강제해야 합니다. 요청에서 받은 임의 경로를 삭제 함수에 전달하면 안 됩니다. 파일 시스템 경쟁 상황/부분 실패/진행 중 세션을 고려한 삭제 시험과 서버 데이터 삭제 어댑터가 추가로 필요합니다.

## 5. 인증 서버와 연결 구조

### 우선 검토할 구조: 서버 중계

```text
Pi ── HTTPS/WSS + 자체 단기 권한 ──> 자체 인증/중계 서버
                                      └── 장기 제공자 API 키 ──> Realtime API
보호자 관리 채널 ── 동의/철회/기기 관리 ──> 자체 서버
```

장점은 제공자 키가 기기에 없고, 서버에서 동의/접근/사용량을 검사하며 활성 전송을 중단할 수 있다는 점입니다. 단점은 서버가 음성 처리 경로에 포함되고 비용·지연·접근통제·국외 이전 검토가 추가된다는 점입니다.

기기→제공자 직접 연결도 가능성을 검토할 수 있지만, **해당 제공자의 선택한 WebSocket 방식이 단기 연결 권한을 실제 지원하는지** 먼저 확인해야 합니다. 다른 전송 방식의 예제를 그대로 적용하지 않습니다. 제공자 토큰의 만료, 세션 수명, 범위와 취소/철회 지원은 서로 다른 개념입니다. 만료 시각만 보고 진행 중 세션이 종료된다고 가정하지 않습니다.

### 구현 순서

1. 테스트 기기를 서버에 등록하고 공개키 또는 검증 가능한 기기 자격증명을 연결합니다. 권장 검토안은 기기가 키 쌍을 생성하고, 서버가 nonce 서명 검증으로 소유를 확인하는 방식입니다. Windows/Pi에서 개인키 보관/복제/분실 대책도 설계합니다.
2. DEVICE_ID는 식별자이며 비밀이나 인증 증거가 아닙니다. ID만 보내는 요청, 임의 ID 교체, 재사용한 nonce는 거부합니다.
3. 장기 제공자 키는 서버의 비밀 저장소에서 관리하고 제품 기기/.env 예제/소스/로그에 배포하지 않습니다. 개발 API 시험에도 제품 경로에 장기 키를 전달하지 않습니다.
4. 단기 권한에 만료, 대상 서버/audience, 기기·세션 범위, 정책/동의 버전, 최소 권한을 연결합니다. 서명/발급자/대상/만료를 서버가 검증합니다. opaque token이면 동일 정보를 서버에서 매핑합니다.
5. HTTPS/WSS와 정상 인증서 검증을 사용합니다. URL query에 토큰을 넣지 않습니다. 선택한 라이브러리가 지원하는 인증 헤더 또는 승인된 인증 프로토콜로 전달하고 인증 완료 전에는 음성을 받지 않습니다.
6. 기기당 동시 세션 제한, 세션 시간/분당 사용량 상한, 인증 실패 rate limit, 키 회전/기기 폐기/권한 철회를 구현합니다.
7. 재연결 때 새 권한과 최신 정책을 확인합니다. 이전 큐를 재전송하지 않습니다. 기기 시간이 잘못되었을 때의 만료 처리도 시험합니다.

`ConnectionGrant`의 현재 만료 검사는 클라이언트 편의 검사일 뿐 서버 인증 검증을 대체하지 않습니다. 지금 자료형에는 토큰 범위/세션/정책 버전이 없으므로 Phase 1 인증 계약에서 확장 여부를 결정해야 합니다. 30초 안전 여유도 실제 토큰 수명에 맞춰 재검토합니다. `revoke_grant()` 추상 메서드가 있다는 사실은 제공자 토큰의 즉시 철회가 가능하다는 증거가 아닙니다.

### 필수 인증 시험

미등록 기기, ID 위조, 서명 위조, nonce 재사용, 다른 기기/대상 서버의 토큰, 만료/철회/빈 토큰, 시간 오차, 발급 서버 장애를 각각 시험합니다. 실패하면 연결/음성 전송을 하지 않고 자원만 정리해야 합니다. 현재 Phase 0의 만료 단위 테스트만으로 이 조건이 검증되지는 않습니다.

## 6. 실제 Windows / Raspberry Pi 5 검증

성인 개발자와 테스트 음원으로 수행합니다. README의 OS별 설치 후 `ai_friend/`에서 실행합니다.

```bash
python main.py --system-info
python main.py --devices
python main.py --test-microphone --input-device <조회한_ID>
python main.py --test-speaker --output-device <조회한_ID>
python main.py --test-audio --input-device <조회한_ID> --output-device <조회한_ID>
python -m pytest -q -m hardware
```

`<조회한_ID>`는 자리표시자이므로 실제 숫자로 바꿉니다. hardware pytest는 환경변수로 선택한 ID를 사용합니다. 장치의 기본 샘플레이트/입출력 채널과 실제 사용 주파수를 기록합니다.

- OS별 5초 녹음과 요청 후 재생을 3회 반복하고 청취해 무음/왜곡/끊김을 확인합니다. 24kHz 출력 PCM 길이는 120,000 프레임이어야 합니다.
- 24kHz 미지원 장치에서 native 주파수 fallback과 음높이/재생 길이를 확인합니다. 이 장치를 확보하지 못하면 해당 항목은 미검증으로 남깁니다.
- 입력 이득을 조절해 RMS/peak/clipping 변화를 확인합니다. 스피커의 디지털 진폭 제한은 실제 음압 제한이 아니므로 안전한 하드웨어 음량을 별도로 측정/검토합니다.
- Ctrl+C, 녹음 중 USB 분리, 출력 장치 점유 후 실패와 장치 재연결을 시험합니다. 실패 후 같은 명령을 다시 실행할 수 있어야 합니다.
- Pi에서 시험 세션을 반복하며 CPU/메모리/장치 오류를 기록합니다. 초기 개발 목표로 30분 반복 시험을 제안하되 제품 내구성 인증으로 취급하지 않습니다.
- `hardware` pytest의 프레임 수 성공은 의미 있는 음성 입력이나 청취 가능 출력을 보장하지 않습니다. 수동 결과를 같이 기록합니다.

현재 완료된 것은 클라우드의 **61개 모의 장치/소프트웨어 테스트**입니다. 실제 장치 3개 테스트는 기본 선택에서 제외됐습니다. Windows/Pi/외부 제공자/인증 서버는 아직 검증되지 않았습니다.

## 7. Realtime 프로토콜·오디오·장애·비용

### 구현 전 확인표

- 실제 프로젝트에서 지원하는 정확한 모델 ID와 권한을 확인해 설정합니다. 모델명을 추측해서 고정하지 않습니다.
- 선택한 WebSocket URL, 인증 방식, 입력/출력 포맷, 샘플레이트/채널/바이트 순서, session 설정과 이벤트 이름을 해당 API 버전 문서로 확인합니다.
- 현재 내부 기준은 24kHz 모노 PCM16입니다. 전송할 때 little-endian PCM과 인코딩 방식을 명시적으로 맞추고, 받은 오디오도 응답의 실제 포맷에 따라 처리합니다. 같은 PCM16 표기만으로 호환성을 가정하지 않습니다.
- 동의/정책 검사는 connect와 send_audio 모두에 필요합니다. 인증/정책 실패가 재시도로 우회되지 않아야 합니다.
- 송수신 큐의 최대 시간/프레임 수, 최대 응답 길이, 연결 timeout과 재시도 상한을 정합니다. 오래된 음성은 재연결 후 재전송하지 않습니다.

### Phase 1의 최소 대화 흐름

초기에는 성인 개발자가 버튼/명령으로 발화를 시작·종료하는 방식으로 시험합니다. 발화 종료 → 입력 commit → 응답 요청 → 음성 출력 → 명시적 취소/종료를 검증합니다. 에코 제거/VAD는 Phase 2 범위입니다. 그 전에는 재생 중 마이크 전송을 중단하는 등 단순한 동작으로 스피커 소리가 다시 입력되어 API 호출이 반복되는 상황을 막습니다.

`BaseRealtimeClient`는 blocking 오디오 함수와 비동기 네트워크를 연결하는 전략이 필요합니다. 오디오 호출 때문에 이벤트 루프가 멈추지 않도록 작업 스레드/유한 큐로 분리하고 스레드 종료까지 시험합니다. cancel_response는 서버 응답 취소뿐 아니라 로컬 재생 큐 정리와 진행 중 재생 중단까지 포함하도록 계약을 정합니다.

### 시험 순서

1. mock 서버로 정상 이벤트, 잘못된 이벤트/포맷, 연결 중단, 중복 이벤트, 취소, shutdown을 시험합니다.
2. 요건 확인된 개발 환경에서 합성/성인 시험 음원으로 짧은 실제 API 요청을 수행합니다. 연결 성공 외에 응답 이벤트와 실제 재생 결과를 확인합니다.
3. 401/403/429/서버 오류/timeout/DNS 실패/느린 네트워크를 주입합니다. 인증 실패는 자동 무한 재시도하지 않고, 일시 장애만 제한된 backoff로 재시도합니다.
4. 수신 취소와 연결 종료 뒤 스트림/작업/큐/버퍼가 남지 않는지 확인합니다. 토큰 갱신과 세션 재연결은 별도 동작으로 시험합니다.
5. 성인 시험 10회 이상에서 발화 종료→첫 응답 오디오의 지연, 전송 프레임 누락, 버퍼 최대 크기, 세션 사용량을 측정합니다. 값이 없으면 성능이 검증됐다고 표시하지 않습니다.

비용은 선택 모델의 최신 가격과 실제 사용량 지표로 산출합니다. 기기당 세션 시간, 동시 연결, 분당/일별 사용량 상한과 서버 측 중단을 구현합니다. 초기 상한은 프로젝트 예산에 맞춰 정하고, 대시보드 알림만으로 강제 중단이 된다고 가정하지 않습니다. 입력/출력 음성, 텍스트 이벤트, 재연결/중복 요청 비용을 함께 검토합니다.

## 8. 로그·저장·아동 시험 운영

- 서버/프록시/WebSocket 라이브러리의 DEBUG 로그와 예외 문자열도 검사합니다. 현재 앱 logger가 안전해도 외부 라이브러리의 payload/header 로그까지 자동 보호되는 것은 아닙니다.
- 합성 문자열을 토큰/전사문/장치 ID에 넣고 시험 후 앱/서버/프록시 로그와 crash report를 검색합니다. 실제 비밀이나 개인정보로 유출 테스트하지 않습니다.
- 오디오/전사문 기본 저장 0건을 파일과 DB 양쪽에서 확인합니다. 제공자 측 보관은 로컬 저장 플래그와 별개이므로 제공자 계약/설정으로 검토합니다.
- 사용자 계정/데이터 삭제는 다른 기기/사용자 자료를 지우지 않아야 합니다. 활성 세션 중 삭제/철회 후 재연결, 일부 삭제 실패, 백업 잔존도 시험합니다.
- 실제 아동 시험 전에는 성인 감독, 즉시 종료 장치/절차, 부적절한 응답 및 개인정보 질문 처리, 사고 신고/대응, 안전한 출력 음압을 검토합니다. AI를 보호자·의료 전문가처럼 소개하거나 효과를 검증했다고 주장하지 않습니다.

## 9. 권장 진행 순서 및 결정 기록

1. **지금:** 성인 개발자용 Windows/Pi 로컬 점검을 진행하고 제공자/개인정보 검토표를 채웁니다.
2. **병행:** mock Realtime 어댑터와 서버 인증/동의 계약을 설계합니다. 실제 아동 전송 차단은 유지합니다.
3. **검토 후:** 성인/합성 음원으로 제한된 실제 API 시험과 중계 서버 개발을 진행합니다.
4. **통합 검증:** 정책 거부/철회/만료/장애/비용 상한/자원 정리/로그 유출을 시험합니다.
5. **아동 시험 전:** 미완료 P0/P1 항목을 확인하고 실제 아동 시험에 필요한 운영 계획을 별도로 검토합니다.
